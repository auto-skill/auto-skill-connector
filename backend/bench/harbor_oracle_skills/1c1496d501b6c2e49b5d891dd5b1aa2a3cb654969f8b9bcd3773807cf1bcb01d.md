# Secret Hygiene

The single most expensive class of mistake when generating code is writing a real
credential into a file that git tracks. Once a secret is committed it is
effectively public — deleting it later does not help, because the value lives in
history and must be rotated. Scanners like gitleaks catch this *after* the fact;
the job here is to never write the secret in the first place, and to catch it if
it slipped in before a commit.

Read this whole file when the skill triggers. It is short on purpose.

## The one rule

**A real secret never goes into a file that git tracks.** Not in source, not in a
config file, not in a `CLAUDE.md`, not in a deploy script, not "just for now to
test it." If a value authenticates to something, it lives in an environment
variable or a secrets manager, and the tracked file reads it from there.

This holds even when the user pastes a real credential and asks to "just hardcode
it for now." Hardcoding it is the failure mode that leaks it. Wire it through env
instead — it is the same amount of work and it is safe.

## When writing code that needs a secret

Never inline the literal. Read it from the environment, and document the variable
without giving it a real value.

**Python**
```python
import os
API_KEY = os.environ["OPENAI_API_KEY"]        # raises clearly if unset
DB_URL  = os.environ.get("DATABASE_URL", "")  # optional, empty default
```

**Node / TypeScript**
```javascript
const apiKey = process.env.OPENAI_API_KEY
if (!apiKey) throw new Error("OPENAI_API_KEY is not set")
```

Then make the requirement discoverable without leaking anything:
- Add the key to a committed `.env.example` with an **empty or dummy** value.
- Make sure `.env` is in `.gitignore` (add it if missing — see the checklist).
- Mention the variable in the README so a new user knows to set it.

**Example**
Instead of:
```python
SSH_PASS = "DzSecure2024!"
```
write:
```python
SSH_PASS = os.environ["SSH_PASS"]   # set in your shell / .env, never committed
```

## Before proposing a commit

Whenever about to suggest `git add` / `git commit`, or whenever the user asks to
commit or push, first check what is staged. Run the scanner on the staged diff
and stop if it flags anything:

```bash
python3 scripts/scan.py --staged
```

(If the script isn't in the project, scan the diff yourself against the patterns
in `references/patterns.md`.) A finding is a blocker, not a warning: surface the
file and line, explain what leaked, and fix it by moving the value to env —
before the commit, not after.

If a finding is a genuine false positive — a test fixture, a documented example,
a public sample key — silence just that spot rather than disabling the check:
- add `# secret-hygiene: ignore` on the line, or
- add a glob to a `.secretignore` file (same syntax as `.gitignore`).

Reach for this sparingly and only when sure; a silenced real secret is worse than
a noisy warning.

If a secret is found that was **already committed** in history, say so plainly and
give the real remediation: the credential must be **rotated** (changed at the
provider), because scrubbing git history does not un-leak a value someone may
already have. See `references/remediation.md` for the exact steps.

## When the user says something leaked

Stay calm and go in this order — it matters:
1. **Rotate first.** Change the credential at its source (new password, revoke +
   reissue the token/key). This is the only step that actually stops the leak.
2. **Then remove it from the code**, moving it to env.
3. **Then clean history** if needed (`git filter-repo` / BFG), knowing this is
   cleanup, not the fix.

Do not reverse this order. A common mistake is scrubbing history first and feeling
safe — the value is still valid until it is rotated.

## Setup checklist for a repo

When starting or hardening a project, make sure:
- `.env` (and `.env.*` except `.env.example`) are in `.gitignore`.
- A committed `.env.example` lists every variable with dummy values.
- No credential appears in any tracked file, including `CLAUDE.md`, `README`,
  CI configs, and deploy scripts.
- For anything beyond a hobby project, a real scanner (gitleaks/trufflehog) runs
  in CI — this skill's hook is a convenience, not a replacement. See
  `references/pre-commit.md` to install the lightweight local hook.

## Scope and honesty

This skill prevents the common, high-cost mistake: a credential written into a
tracked file. It is not a full secrets-management solution and not a substitute
for a dedicated scanner on git history. When the stakes are real (production, a
public repo, anything with user data), say so and point to gitleaks/trufflehog in
CI alongside these habits.
